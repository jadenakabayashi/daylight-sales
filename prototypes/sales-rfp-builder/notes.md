## What this is

Entry point: the real Valt Rate Card screen (`Refs/Foundation` doesn't have a screenshot of this, but the user supplied a live screenshot of `valt-daylight-media.vercel.app/inventory` — reproduced here with a "+ New RFP" button added, since the real screen doesn't have one yet). **Tabbar**: Embedded, Newsletters, DAI, Social, Custom, per the user's explicit direction — Embedded (internally still keyed `ratecard`), Newsletters, and DAI are all real/clickable now; Social and Custom stay decorative (no underlying data pulled in for those yet — this workbook only has three named sheets: the main roster, DAI, and Newsletters, all three of which are now wired up). Fill Status and Talent, present in the original screenshot's tabbar, were dropped entirely rather than kept decorative. The sidebar's Inventory sub-nav still lists all 8 original items (Rate Card, Fill Status, Embedded, DAI, Custom, Newsletters, Social, Talent) unchanged — this was a tabbar-only change.

All three tabs share one generic filter/sort/group engine (`TABS`/`tabState` in `prototype.html`, keyed by tab) rather than each having bespoke logic — any column, on any tab, can be filtered, sorted, or grouped by, adapted to that column's data type, and each tab keeps its own independent filter/sort/group state when you switch away and back. The four decorative "Inventory Type / Status / Roster / Contact" toolbar dropdowns from the original screenshot were removed entirely (no data ever backed them) — the per-column ▾ menus were the only filter/sort/group UI for a while.

**Toolbar-level Filter / Sort / Group**, next to the search bar, were then added on top of that — per the user's explicit ask, deliberately redundant with the per-column menus, for discoverability (a user scanning the toolbar shouldn't have to already know that every column header hides a menu). All three now share the same "+ Add another" multi-row pattern:
- **Sort ▾ / Group ▾**: each row is a "Select category…" dropdown alongside a direction dropdown defaulting to **Descending**. `state().sort` / `state().group` are each an ordered array of `{field, dir}` — sorting applies each level as a tiebreaker in order, and grouping **nests** (group by level 1, then within each bucket sub-group by level 2, indented one step further, and so on).
- **Filter ▾**: same row, same side-by-side layout as Sort/Group — `[category select] [criteria control] [✕]` all in one line — but since a filter's "correlative options" aren't just ascending/descending, the criteria control is type-specific: a min/max range for numeric columns, a text box for free-text columns, both inline in the row exactly like Sort/Group's direction dropdown. **Multiselect columns (Genre, Host Location, Drops, etc.) are the one case that can't fit a whole checklist inline** — so that row's second control is itself a compact dropdown: a summary button (starts as "Select values", becomes "Comedy" or "Comedy, News" or "4 selected" as boxes get checked) that opens a small popover of checkboxes directly beneath it, nested inside the already-open Filter panel. Checking a box updates the summary text immediately without closing the popover, so multiple values can be picked in one go. `state().filterRows` holds the ordered list of *which columns* have a row in the panel (ordinary strings, not `{field,dir}` — a filter's real criteria still lives in `state().filters`, keyed by column, same as before); picking a different category in a row abandons that row's old filter and starts a blank one for the new column.
- Every row past the first can be individually removed (✕) on all three panels; removing the last one leaves a single blank row rather than an empty panel. Setting a filter via a column's own header menu (rather than the toolbar) still shows up as a row next time the toolbar Filter panel is opened — `renderFilterLevels()` reconciles `state().filterRows` against `state().filters` on every open, so the two entry points can't silently disagree about what's active.
- All controls read from and write to the exact same `state().filters` / `state().sort` / `state().group` the column menus use — there are two UIs but one underlying state per tab, so setting something from the toolbar and then opening that column's header menu shows it already applied (and vice versa), and the toolbar buttons pick up a highlighted "has a value" style whenever anything's active. Chips reflect every active level individually (e.g. "Sort 1: Genre (desc)", "Sort 2: Net CPM (asc)", one chip per active filter value) and are each independently removable. Column-header quick-actions (clicking a header's label, or its menu's "Sort ascending/descending"/"Group by this column") still work as one-click single-level shortcuts — they collapse sort/group down to that one criterion rather than going through the multi-row UI.
- Only one of {a column's own menu, the toolbar's own panel} is ever open at once (opening either closes all the others) — this was a deliberate simplification so a filter control never has to reconcile being edited from two open surfaces simultaneously.
- **View ▾** ("Edit Columns"), the fourth toolbar control: reorder columns by drag handle and show/hide each with a toggle, per the reference screenshot the user supplied — reproduced for interaction pattern (drag handle, toggle switches, a locked always-visible first column, a "Reset" link) but restyled entirely in this prototype's own dark tokens rather than the reference's light UI. Column view state (`columnView[tab] = {order, hidden}`) is separate from `state().filters/sort/group` and per-tab like everything else — hiding a column from the table doesn't remove it from the Filter/Sort/Group column pickers, so you can still filter/sort/group by something you've hidden. The identifying column ("Name") is locked: always first, always visible, not draggable, shown as "Locked" text instead of a toggle. Drag-reorder moves the existing DOM node directly (`insertBefore`/`after`) rather than re-rendering the list on every `dragover` — replacing the actively-dragged element mid-drag would abort the native HTML5 drag session; the list only fully re-renders once, on `dragend`. Toggling visibility flips just the clicked button's own class rather than re-rendering its container, for the same reason clicking "+ Add another" elsewhere in this toolbar doesn't close its own panel: replacing an ancestor of the just-clicked element mid-click detaches it before the click event finishes bubbling to `document`'s "click outside closes the panel" listener, which then misfires.

- **Newsletters tab**: populated from the same workbook's own **"Daylight Newsletters" sheet** — by far the smallest of the three (only **3 real newsletters** have data; the sheet's other ~950 rows are blank). Its own 21 real columns: Name, Writer, Genre, Description, Link, Male/Female %, Age Breakout (a free-text age-bracket breakdown, not a single number), Subscribers, Net CPM, Net Rate, Preferred Code, Open Rate, CTR %, Channel Advertisers, Hosting Platform (Substack/Omnisend), Frequency, SOV, Release Days, Audience Location, Sales Pitch. Kept two real messiness artifacts as-is rather than cleaning them up: the Genre column has a real typo ("Poltiics/News"), and the Link column mixes real URLs with one non-URL value ("Only available via email" for The Shawn Ryan Show newsletter) — the renderer only turns a cell into an "Open ↗" link if it actually starts with `http`, otherwise it shows the raw text. With only 3 rows, grouping by any column is much less meaningful here than on the other two tabs (most groups will just be 1 row) — implemented for consistency, not because it's especially useful at this sample size.
- **DAI tab**: populated from the same workbook's own **"Daylight DAI" sheet** — a separate, much smaller inventory (11 real shows, vs. 58 embedded) confirming `business-systems.md`'s note that DAI is "tracked separately from embedded ads." Its own 14 real columns: Name, Hosts, Genre, Description, Apple RSS, Male/Female %, Median Age, **Monthly Impressions** (DAI's own delivery metric, distinct from the embedded roster's Avg. - Active filters, the current sort, and the current group all show as removable chips above the table, plus a single "Clear all."
- Implementation note: re-rendering only ever touches table rows, chips, and header state classes/arrows — it never rebuilds the header `<th>`/menu DOM itself, so typing in a range/text filter doesn't lose input focus mid-keystroke.

From there:

1. **Start** — upload a brief (simulated scrape) or build criteria from scratch.
2. **RFP Response** — an editable draft of advertiser, category, direct/indirect competitors, target genres, CPM range, DAI SOV, host requirements — all editable regardless of path.
3. **Vetting Pass 1** — runs a real, generalized scoring engine (not a lookup table) against the actual Rate Card data:
   - Genre/format filter (hard filter — shows either enter the candidate pool or land in "Filtered out")
   - Competitive-exclusivity check (direct/indirect competitor already on a show)
   - Previous-vetting-history check (advertiser previously declined by a show)
   - Renewal check (advertiser already a current advertiser — surfaced as an upsell, not a fresh slot)
   - CPM-range check (below/above the RFP's requested range)
   - Buckets: Recommended / Flagged / Eliminated / Filtered out, each show a card with its actual reason(s) surfaced inline.
4. **Recommendations are overridable, not final.** Each Recommended/Flagged card has a "Remove from proposal" toggle; each Eliminated card has an "Include anyway (override)" toggle — Sales can disagree with the system in either direction. A live proposal bar tracks the resulting count, split into shows **already approved** for this brand vs. shows **not yet vetted with the show itself** (per the show's own vetting history — approved/declined/unvetted, tracked separately from the exclusivity/CPM checks above). The "+ New RFP" entry point is a modal overlay over the Rate Card (not a page navigation), so the underlying Rate Card stays visible/dimmed behind it.
5. **Send to Ad Ops.** The closing CTA sends every un-vetted show in the final (post-override) proposal onward — the copy explains that Ad Ops will confirm each one directly with the show, log the approve/decline "whys" back onto the RFP, and the finalized list then goes back to the **agency** that submitted the original request (a new Agency field on the RFP Response, e.g. "Oxford Road" for the sample). Shows already marked approved for this brand skip that step.

This matches the RFP flow's first stage as described in `daylight-knowledge/references/business-systems.md` ("RFP → vetting → submission") and the more precise 4-step version from the 2026-07-27 VALT product session (`vault-product-development.md`): exclusivity check → previous-vetting check → demo/criteria filter → conflict vetting. - **"Send to Ad Ops" is a one-way simulated handoff** — it shows what gets sent and the resulting copy, but there's no real Ad Ops-side inbox, no actual response loop, and no real writing of "whys" back onto a stored RFP record. Next real step would be an Ad Ops-facing queue that consumes this handoff and lets them log approve/decline per show.
- Episodic category exclusivity and IO-specific conflict vetting (the deeper Ad Ops-owned checks beyond simple brand-vetting-history) are still out of scope for this pass.
- Only 4 real fabricated-conflict examples (plus 1 fabricated approval) exist across the whole 58-show roster; a real build would need this data sourced from an actual Ad Ops vetting-log/CRM, not invented.
- The "Upload an RFP" path doesn't do real document parsing (no client-side PDF/DOCX parser) — it always loads the Babbel sample as a stand-in for "scrape succeeded." A real build would need an actual extraction step (the kind of thing `scripts/extract_ref.py` does for this project's own research, generalized to arbitrary uploaded briefs).
- No persistence — refreshing the page resets all state. Not needed for a first-pass prototype but worth flagging if this gets handed to another builder.
- **DAI isn't wired into the RFP vetting flow yet** — the Babbel brief itself asks to "present DAI at 20% SOV," so a real Pass 1 would need to pull candidate shows from both the embedded roster and the DAI sheet together (and reconcile that a show's DAI and embedded CPM/advertiser lists aren't identical). Scoped out of this pass since the ask was specifically to populate the DAI tab, not extend vetting to it.
